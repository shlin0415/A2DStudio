# A2D Studio 后续开发计划

> 调研基准：2026-10-12\
> 最近更新：2026-10-22（字幕与舞台动作同步；新增脱敏时序诊断；确认项目包素材范围）\
> 目的：收敛产品目标、整理项目现状，并给出可验证的下一步。
> 状态：路线建议；不是 Rust 重写或大规模删档的执行授权。

## 结论先行

A2D Studio 应从“持续跟随 LingChat 分支改动的 fork”收敛为“以剧本项目为中心的 CP 内容创作与播放工具”。LingChat 继续作为上游参考和候选底座，但不再是产品需求本身。

推荐顺序：

1. 暂停新增旁支功能和大批量 upstream 合并，先冻结 A2D 必须交付的用户流程。
2. 先完成一轮可复现的四服务基线，并让 A2D Studio 页面使用独立产品入口；这一步先消除重复和误导控件，再判断哪些舞台视觉组件值得复用。
3. 用同一段短剧本验收编辑、双人合成、回放和保存，再收敛一个可移植的 A2D 项目格式。
4. 用该项目样例验证当前 Python/Vue 与上游 Rust 底座，只选一个长期实现底座。
5. 手动创作竖切片稳定后，再扩展自动生成、自媒体画面和睡前 ASMR。

这条路线保留了“精简甚至大改”的空间，但把重写放在需求和验证之后。现在直接重写会同时重做脚本格式、语音调用、播放状态和存档，且无法从文档判断哪部分旧实现值得搬。

## 1. A2D 原始目标

历史记录对产品意图的描述基本一致：基于 LingChat 做一个可手动、可自动的 A2D Studio，包含自动 CP 内容创作、剧本编辑和 ASMR 播放。更细的定义是：

- **CP 内容创作**：生成双角色对话和情境描写，产出可阅读、可播放的 CP 故事。
- **自媒体/知识表达**：通过 CP 对话配合屏幕上的图片和文字，讲解知识或代码。这里没有明确要求自动发布到社交平台，也没有确认必须导出视频。
- **手动剧本编辑**：逐句修改、指定说话者、调整情绪、重生成单句语音、预览并导出完整剧本。
- **自动创作**：LLM 可以生成或续写，但创作者应能在开始前查看提示词、随时停下、切换手动、选择下一位说话者并补充中途提示。
- **ASMR**：同一剧本和播放能力的一个内容/播放模式，重点是适合休息时聆听的文案、语气和声音；播放控制应支持长音频体验。
- **设备目标**：历史目标提到电脑、手机、Web 和桌宠。它们是整体方向，不代表第一阶段必须同时交付四种壳层。

主要依据：被忽视日志中的原始定位和具体解释，见 `human-chat.md:776-820`、`human-chat.md:2221-2279`。这些记录目前被本地排除规则忽略，适合作为历史来源，不应继续承担活跃路线图的职责。

## 3. 建议的产品边界

把 A2D 的中心从“LingChat 聊天记录/内部对象”转为一个独立、可保存、可搬运的 **A2D 剧本项目**。应用的其他功能都围绕这个项目工作。

**已回答问卷及后续补充形成的当前倾向（可随验证调整）：** CP 故事优先，A2D 独立发展，剧本项目文件作为核心产物；手动创作先完整可用，LLM 作为可选输入；先做响应式 Web；界面先围绕两位主角，但项目格式不限制说话者数量；CP、知识表达和 ASMR 共用项目基础；保留 GSV1/GSV2 双路语音；在线 LLM 由用户选择，项目和音频默认留在本机；选择性复用 LingChat，历史材料逐步整理；Rust 只做有边界的样例验证后再决定。LLM 首阶段以 OpenAI 兼容接口为边界，近期优先验证 DeepSeek 与 MiMo，Gemini 暂缓；“兼容接口”不等于任意厂商/模型已经通过 A2D 页面切换和流式生成验收。`fic_*` 仍是实验代码，问卷备注表明其用途目前已不清晰，重新投入前先做短小的代码/产物盘点，不把它预设为核心产品。

**已确认的三个界面/项目细节：** `/studio` 作为编辑与预览工作台，另有明确的专注播放状态（旧地址 `/stage` 已从 A2D 路由移除）；编辑中的项目使用可读写的项目目录，交付时可导出便携压缩包；项目记录每个说话者选用的声音配置/引用，本机的 GSV 服务地址和密钥留在应用本地配置中，不打包进项目。

一个剧本项目至少需要描述：

- 项目标题、剧本模式（CP 故事 / 知识表达 / ASMR）和角色/说话者；
- 有稳定 ID 和顺序的台词行，包含显示文本、语音文本、情绪、动作/旁白和说话者；
- 可选场景、背景、屏幕图片/文字，以及它们对应的素材引用；
- 可选音频文件及其生成参数/状态；
- 一个明确的格式版本号，方便未来修改格式时显式迁移。

最小运行边界：

```text
Vue/Web 创作与播放界面
        │
A2D 剧本项目与素材（单一项目格式）
        │
编辑 / 生成 / 合成 / 预览 / 导入导出
        ├── LLM：可选；生成结果回到同一编辑流程
        ├── GSV1：角色 A 的独立 TTS 服务
        └── GSV2：角色 B 的独立 TTS 服务
```

具体约束：

1. **无 LLM 仍然能完成完整手动流程。** LLM 是内容输入方式，不是剧本编辑器和播放器的运行前提。
2. **改一句只影响该句及其确实依赖的产物。** 台词、情绪或说话者变化需要明确音频失效/重生成；不能静默播放旧音频。
3. **GSV 服务保持外部边界。** A2D 负责选对服务、传递角色/情绪参数和管理音频，不把 GSV1/GSV2 的服务进程塞进核心业务逻辑。
4. **工作项目以目录形式保存，交付时导出便携压缩包。** 剧本和素材使用项目内相对路径；暂不为项目列表、云同步、多人协作另建数据库/同步系统。
5. **项目格式要与 LingChat 内部数据解耦。** 这样才可用同一份 A2D 项目评估 Python 和 Rust 底座，而无需同时维护两套 A2D 数据模型。
6. **A2D 页面拥有自己的产品壳。** 不把旧 `GameDialog` 整体叠放在 A2D 编辑/播放界面下，也不靠 CSS 隐藏整块旧功能来制造“已解耦”；逐项判断旧组件是复用视觉能力、改成 A2D 操作，还是从 `/studio` 移除。页面验收看用户能否一眼分辨当前可用操作，且操作确实进入 A2D 项目/播放链路。
7. **声音身份属于项目，服务端点属于本机。** 项目保存说话者到声音配置/素材引用的映射，确保重开时知道原有选音；GSV 地址、运行方式及任何密钥由本机配置提供，不写入可搬运项目。

### 阶段 1：可复现的运行基线与 A2D Stage 解耦

**当前状态：大部分通过（更新至 2026-10-18）。** 启动器从空闲端口通过预检启动，前端、后端、GSV1、GSV2 均就绪并分别记录日志；停止后 PID 退出、目标端口释放。Stage 已卸载旧 `GameDialog`/聊天输入路径；专注模式不会自动播放。run `20261018-211959-b389f461` 在同一次全新启动中完成双 GSV 合成、两次顺序播放、应用 ZIP 下载、同包重开和重播，随后确认四个服务进程与目标端口均已释放。前端 100 项和生产构建通过；类型检查保留 6 个未修改 LingChat 文件中的既有错误。当前包只收录音频，不包含图片/背景等外部素材。没有写入用户项目目录。

**工作**

- 按本地正确 Python 环境启动前端、Python API、GSV1、GSV2；明确端口、健康检查方式和日志位置。
- 先逐项盘点 `/studio` 可见控件及其事件目标，标为“保留并验证 / 改为 A2D 操作 / 从 A2D 页面移除”。移除旧聊天输入/发送路径与只属于 LingChat 的控制项；仅在确认职责后复用背景、角色等视觉组件，不把整套旧聊天壳藏到 A2D 面板下。
- 修正并验证背景资源的 URL 解析；验收截图中应加载预期背景，且角色、字幕、剧本面板层次互不遮挡。
- 用固定的短剧本（每个角色至少一句）验证从页面提交、后端分流、GSV 合成、音频回传/播放、保存的完整路径；此后通过新的一键启动/停止入口从干净状态重复一次。
- 失败时保存前后端与两个 GSV 服务的相关日志片段和时间戳，并标出失败在哪个边界；不要把模型内部长日志无差别复制进 human-chat。
- 区分“服务未启动/配置错误”“API 契约不匹配”“剧本解析失败”“音频播放状态错误”，避免只凭一个前端 toast 判断根因。

**完成标准**：同一份操作步骤可由一键入口从干净状态启动并重复，停止后四个子服务均退出；两路声音都能播放；项目可保存并重新载入；A2D Stage 默认是清楚的编辑/预览工作台，并能进入专注播放状态；页面不再显示旧聊天占位名/重复旧对话控件，保留的每个操作都有明确 A2D 用途和有效事件；背景资源正常加载；失败有明确错误和对应日志。

### 阶段 2：定下 A2D 项目最小格式

**现有实现检查（2026-10-18，尚非最终格式决定）：** 新项目 ZIP 格式为 v1，内部仍包着现有快照 v2（`script`、`game`、`stages`，导入器接受 v1/v2）；项目脚本存储项目名、说话者 key 和相对 WAV 路径，ZIP 外层列出 `project.json` 和 `assets/audio/line-####.wav`。浏览器已从应用导出实际下载 752 字节 ZIP，并重新打开同一文件；项目名、说话人、台词、音频状态恢复。测试样例内 WAV 为 9,644 字节，导出前后哈希一致。`script.lines[].speaker` 是 `script_role_key`，本机后端用它查找角色配置；导出器不从本机 `.env`/语音配置复制 endpoint 或 credential，本次手动样例包未发现密钥字段，但开放的 `overlay.gsv_params` 字段仍需在最终格式里白名单约束。换机器后重新合成仍要求对应本机角色 key 存在。当前 envelope 仍携带 `gameRoles/presentRoleIds` 运行时字段，之后应通过样例判断其是否属于 A2D 项目契约。图片、背景和其他外部素材尚未打包，故目前只验证了含脚本与 WAV 的跨目录 ZIP。

**工作**

- 从现有 `ScriptLine`、`Stage`、`LineOverlay` 和前端 TS 类型中抽出真正需要的字段，不新造一个大而全格式。
- 准备一份小型样例项目，覆盖两位说话者、旁白、情绪、一个背景、一个屏幕文字或图片、已生成和未生成音频两种状态。
- 定义单项目文件/素材目录的保存、复制、导入和导出规则；路径使用项目内相对引用，避免绑定到本机绝对路径。
- 明确本地编辑目录和交付压缩包的生成/重开规则；压缩包解开到另一目录后，台词、素材引用、已生成音频和说话者声音映射仍可恢复。
- 项目文件只保存创作与播放所需的数据，不把 LingChat 聊天输入框状态、旧对话 UI 状态或 `gameRoles/presentRoleIds` 等运行态字段直接当成 A2D 项目格式；确有必要保留的角色/素材引用要由 A2D 项目模型明确定义。
- 验证格式能完整表达三类内容（CP 故事、知识表达、ASMR），差异作为项目配置/提示词，不复制三套台词模型。

**完成标准**：手写 JSON 样例可读可校验；加载后再保存不会丢台词顺序、角色、素材引用或音频状态；不依赖 LingChat 聊天历史才能还原内容。

### 阶段 3：一次有边界的 Rust 底座验证

在开始搬代码之前，用阶段 2 的同一份样例做一个短验证，不同时实现两套 A2D：

1. Rust 上游能否把 A2D 项目打开、逐句编辑、保存和导出？
2. 是否能按不同说话者分别调用现有 GSV1/GSV2 服务并单句重生成？
3. 播放时是否能保持台词、音频、屏幕素材顺序一致？
4. 加 A2D 的图片/文字舞台是否能放在清晰的扩展边界中，而不用重写上游剧本编辑器核心？
5. Web/桌面/手机目标能否按当前团队的时间与部署方式维护？运行 GSV 的机器与播放端如何连接？
6. 上游许可证、角色素材和默认资源能否满足预期的发布/分发方式？

**选择规则**：

- 只有上述 A2D 必须流程均可验证、扩展面清楚，且维护成本低于继续修补当前 Python fork，才选 Rust 作为新底座。
- 若 Rust 验证不通过，先以当前 Python/Vue 代码恢复并完成 A2D 的最小竖切片；同时停止把 Python LingChat 当作长期可同步的上游。等 A2D 需求稳定后再根据实际部署需求选独立运行形态。
- 决策后只维护一条 A2D 实现路线，不做长期双后端、不做隐藏回退层。确有旧项目数据需要保留时，做一个明确的一次性导入工具，不把兼容逻辑散进主流程。

**同一样例的有限验证结果（2026-10-18，官方 LingChat v0.5.2 / `848fd3448c20ca32e0436a498d20e85f63393e7f`，源码检查，未运行 Tauri 应用）：** 用通过 A2D 浏览器导入、导出落盘、同应用重开和 WAV 播放的 ZIP 样例 `tmp/a2d-export-browser-validation-20261018/a2d-export-roundtrip-20261018-fixed.a2d.zip` 对照上游 `/script-editor` 合约。该包是 `a2d-studio-project` v1，内有 envelope/script v2、逐句 `speaker`/文本/相对 WAV 路径；上游编辑器的 `editor_list_scripts`、`editor_read_script`、`editor_read_chapter`、`editor_write_chapter` 等命令读写 LingChat 游戏数据目录中的 `story_config.yaml` 与 `Chapters/*.yaml`，没有查到 A2D ZIP 的导入/导出命令或 `a2d-studio-project` 格式适配。通用角色压缩包能力不能当成 A2D 项目包支持。

- 上游 `TtsConfig` 只有一个 `gsv_api_url`；`VoiceMaker` 为角色读取独立的音色、参考音频和模型配置，但创建每个 GSV adapter 时仍传入同一个全局服务地址。因此当前源码不能证明可按 A2D 角色分别路由到 GSV1 与 GSV2。
- 上游章节事件执行器在章节内按 YAML 数组顺序推进，章节结束事件还可转到其他章节；试玩复用 LingChat 游戏引擎和会话状态。编辑器文档注明 AI 对话事件会调用 LLM。这和 A2D 当前的逐句手动编辑、指定双 GSV、按清单播放且无 LLM 的路径不是同一数据/执行契约。
- **当前里程碑选择 Python/Vue 作为唯一 A2D 实现底座**：本次在它上面已验证逐句编辑、GSV1/GSV2 手动合成与顺序播放、专注播放、ZIP 样例导入和音频播放。Rust 上游若要承载同一项目，至少需要明确的 A2D 项目适配、双 GSV endpoint 路由及独立 A2D 播放入口；把它们补齐已经超出“用同一样例做小范围验证”，此时平行实现会重复产品链路。此结论针对当前样例与里程碑，不表示 Rust 无法扩展，也不授权整体迁移。
- 这次没有构建或启动 Rust/Tauri 应用；评估范围是固定 SHA 的本地源码合约与同一份 ZIP 结构。平台部署成本、许可证/资源分发仍需在未来选定发布形态时单独核对。浏览器实际导出/重开现已通过，但 A2D ZIP 的最终格式边界及图片/背景打包仍待阶段 2 继续收敛。

**完成标准**：写下一页以内的结果，明确采用的底座、没通过的必须项和决定依据；没有进入完整重写。

### 阶段 4：完成 A2D 手动创作竖切片

**范围**：项目打开/保存、逐句编辑、选择角色和情绪、单句重新合成、预览/暂停/跳转、完整播放、导入导出。全流程不调用 LLM。

**当前实现进度（2026-10-18）：** 手动逐句编辑、说话人到 GSV1/GSV2 路由、真实单句合成、两句顺序回放、专注播放不自动启动、应用导出 ZIP 落盘、同一文件重新打开并恢复音频均已通过。导出曾因点击后立即 revoke Blob URL 而取消；增加 1000 ms 延迟后，Chromium 下载完整落盘。run `20261018-211959-b389f461` 已在同一全新启动批次组合验证双 GSV 合成、两次顺序播放、ZIP 下载、同包重开和重播；前端 100 项及生产构建通过。类型检查仍有 6 个未修改 LingChat 文件中的既有错误。ZIP 目前只包含脚本和音频，不含图片/背景。

**验收样例**：用户创建一段 10 行以内的双人脚本，在其中修改一句并重做该句音频，听完全段，关闭再打开项目后继续播放，并导出一个包含脚本和引用素材的项目包。

**完成标准**：手动流程能在实际 GSV1/GSV2 服务上跑通；改句不会错播旧音频或把后续角色顺序打乱；导出后另一份目录可以重新打开。

### 阶段 5：恢复自动创作和三种内容模式

- 将自动生成放在手动流程之上：LLM 输出必须进入同一份 A2D 项目并经过格式校验，不能另建只在自动模式可用的运行态。
- DeepSeek、MiMo 先分别验证 A2D 实际配置读取、模型选择和流式结束/错误处理；传输层冒烟通过不代表 UI 切换通过。Gemini 暂不进入当前里程碑。
- 优先支持“给主题/大纲生成双人 CP 对话”的一条稳定路径；保留预览提示词、停止生成、手动继续、选择下一位说话者和中途补充要求。
- 再用同一条链路验证知识/代码讲解：台词中能定位到对应图片或屏幕文字，播放顺序一致。
- ASMR 首先验证剧本语气与双人音色、连续播放/循环/音量等用户可感知体验；睡眠计时、复杂混音等在确认必要后再加。
- `fic_*` 管线先做一次范围受限的代码入口/输出格式盘点；能直接产出可编辑 A2D 项目的部分再纳入核心，不能复用的部分继续标为实验，暂不扩展或删除。问卷备注是用户目前已不太记得其用途，这意味着不能把它列作第一阶段前置工作。

**完成标准**：自动生成、人工修改、重新合成、项目导出使用同一份内容状态；不因切换模式丢掉人工编辑。

### 阶段 6：设备和交付范围

- 先把创作/播放页面做成桌面浏览器和手机浏览器都能完成阶段 4 的核心任务；以实际触屏操作检查编辑、选择角色、播放和素材布局。
- 再决定是否需要原生桌面/手机包或桌宠入口。它们是交付壳层，不能迫使剧本模型与内容管线复制一份。
- 在“自媒体工具”实际需要明确前，交付可播放舞台和项目包；不要默认增加视频渲染、社交账号登录或自动发布。

**完成标准**：有一条确认过的使用设备/部署路径；范围外的入口不会阻塞核心创作流程。
