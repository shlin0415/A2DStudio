# A2D Studio 方向澄清问题清单

> 用途：收集安奈对产品方向的倾向，作为 [后续开发计划](a2d-studio-development-plan.md) 的输入。\
> 建议先回答第 1 轮 5 题；后面几轮的问题会受前面的选择影响，可以之后再填。也可以一次填完。
> 选项不是考试答案；推荐项只是都莉根据目前仓库和历史目标给出的起点。每题都可以写自己的 D 选项。

## 第 1 轮：先定产品方向

这五个问题可以独立回答，决定后续计划从哪里开始。

### Q1. A2D 第一阶段最先要让用户获得什么价值？

- A. 创作和播放 CP 故事
- B. 用 CP 对话讲解知识/代码，制作自媒体内容
- C. 创作适合休息时听的 ASMR 内容
- **推荐：A**。项目名和最初的“Auto CP”定位最明确；它也能先验证剧本、双人语音和播放这条共同基础。
- **你的答案 / 补充：** __A____

### Q2. A2D 和 LingChat 的长期关系是什么？

- A. 继续作为 LingChat fork，尽量跟随上游并保留整体功能
- B. 成为独立的 A2D 产品，只复用真正需要的 LingChat 能力
- C. 作为 LingChat 内部的一个剧本/创作模式
- **推荐：B**。A2D 的目标已比普通聊天功能窄而专；独立产品边界能让它按自己的剧本和播放需求取舍。
- **你的答案 / 补充：** __B____

### Q3. 用户最终主要在 A2D 里保存和交付什么？

- A. 可继续编辑的剧本项目，带素材/音频并可直接播放
- B. 合成好的完整音频节目
- C. 渲染好的视频或可发布内容
- **推荐：A**。项目文件可以作为编辑、播放、音频和未来导出的共同来源；视频是否必要可以后续再定。
- **你的答案 / 补充：** __A____

### Q4. 手动编辑和 AI 自动创作谁应该是第一阶段的基础？

- A. 一键自动生成并播放优先，人工只做少量修改
- B. 手动脚本完整可用，AI 生成是可选入口
- C. 先做纯手动，暂不考虑 AI 生成
- **推荐：B**。这样即使 LLM 不可用也能创作，同时保留“自动磕 CP”的核心方向。
- **你的答案 / 补充：** __B____

### Q5. 第一阶段优先支持哪种使用界面？

- A. 桌面浏览器
- B. 手机和桌面浏览器都能完成核心操作
- C. 先做 Windows 桌面应用/桌宠
- **推荐：B**。响应式 Web 可以先覆盖电脑和手机，不必先承担原生安装包和桌宠的维护成本。
- **你的答案 / 补充：** __B____

## 第 2 轮：明确内容和创作流程

这些问题会进一步收窄用户流程，建议回答完第 1 轮后再填。

### Q6. 你最希望 A2D 服务哪类主要用户？

- A. 自己写/改故事的创作者
- B. 想直接收听或游玩别人作品的用户
- C. 用对话形式制作知识、课程或代码内容的创作者
- **推荐：A**。当前最明确的未完成能力集中在剧本编辑、逐句重做语音和导出。
- **你的答案 / 补充：** __A____

### Q7. 自动生成剧本时，创作者应该怎样介入？

- A. 输入主题后整篇生成并自动合成语音
- B. 分段生成，允许检查、修改、停止、手动续写和补充要求
- C. 第一版只提供 AI 改写，不负责从零生成
- **推荐：B**。它保留自动生成效率，也符合历史记录中“随时切手动、指定说话者、追加提示”的要求。
- **你的答案 / 补充：** __B____

### Q8. “自媒体工具”第一版具体做到哪一步？

- A. 剧本播放时显示背景、图片和文字，项目可导出
- B. 把剧本自动渲染成 MP4
- C. 直接连接社交账号并自动发布
- **推荐：A**。历史描述明确提到 CP 对话配合屏幕图片和文字；没有证据表明自动渲染/发布是首要需求。
- **你的答案 / 补充：** __A____

### Q9. ASMR 应该是怎样的产品能力？

- A. 只是剧本的一个内容标签
- B. 同一项目里的播放模式，提供适合长听的播放控制
- C. 与剧本编辑器分开的独立播放器
- **推荐：B**。历史目标把 ASMR 建立在剧本编辑器之上；先共享内容和播放，再按需要增加睡眠计时等控制。
- **你的答案 / 补充：** __B____

### Q10. 首版的说话者数量如何处理？

- A. 只支持一对 CP 的两位说话者
- B. 从第一版就完整支持任意人数、多组关系和复杂群戏
- C. 界面围绕两位主角，剧本格式不把人数写死
- **推荐：C**。双人流程容易验收，也避免以后为了增加第三个说话者重做存档格式。
- **你的答案 / 补充：** __C____

### Q11. 桌宠应在 A2D 的什么位置？

- A. 必须与第一版创作/播放流程一起交付
- B. 核心剧本工具稳定后再接入
- C. A2D 不需要桌宠
- **推荐：B**。桌宠是历史设备目标之一，但不是验证剧本、TTS 和导出链路的前提。
- **你的答案 / 补充：** __B____

## 第 3 轮：选择技术和数据边界

这些问题依赖前面选定的产品形态。它们用于避免在没有目标流程时先重写底层。

### Q12. Python 到 Rust 的迁移应如何决定？

- A. 先继续 Python，等 A2D 核心流程稳定后再评估
- B. 用一个真实 A2D 样例验证上游 Rust，再决定是否迁移
- C. 现在就以 Rust 重写为主线
- **推荐：B**。LingChat Python 发行版已半归档，但当前本地仓库并不是 Rust 工程；需要用 A2D 的实际流程判断 Rust 是否合适。
- **你的答案 / 补充：** __B____

### Q13. A2D 是否需要保留 LingChat 的通用聊天功能？

- A. 尽可能保留所有聊天、记忆、角色、桌宠等功能
- B. 只保留 A2D 创作和播放所需的能力
- C. 保留通用设置/模型配置等基础设施，但产品页面聚焦 A2D
- **推荐：C**。减少无关产品面，同时复用已有配置、LLM 或角色能力前仍要逐项确认实际价值。
- **你的答案 / 补充：** __C____

### Q14. LLM 接入范围应该怎样控制？

- A. 继承 LingChat 的全部模型/提供商能力
- B. 首版只支持 OpenAI 兼容接口
- C. 只接一个指定模型，先不抽象提供商
- **推荐：B**。覆盖面足够大，接口也能保持窄；后续只有具体用户需求出现时再扩展。
- **你的答案 / 补充：** __B____ OpenAI 兼容接口应该也支持 deepseek mimo gemini 等模型是吗？我有点忘了

### Q15. 第一条可用 TTS 流程以什么为准？

- A. 先打通当前两路 GSV1/GSV2 角色语音服务
- B. 首版就兼容多个 TTS 厂商和多种本地引擎
- C. 直接改用 LingChat Rust 版内置语音引擎
- **推荐：A**。这是当前项目已有的关键使用场景，也能直接验证双角色路由和实际播放。
- **你的答案 / 补充：** __A____

### Q16. 剧本项目首先应该如何保存？

- A. 一个可搬运的项目目录/压缩包，包含剧本和引用素材
- B. 应用数据库是唯一保存方式
- C. 默认云端保存并在设备间同步
- **推荐：A**。先验证项目能保存、复制、重开和导出，避免数据库/云同步扩大第一阶段范围。
- **你的答案 / 补充：** __A____

### Q17. 旧数据兼容的范围是什么？

- A. 尽量兼容所有 LingChat 历史对话和存档
- B. 只迁移确实要继续使用的 A2D 剧本/项目
- C. 新格式重新开始，不提供导入
- **推荐：B**。保留有价值的 A2D 创作成果，但不让通用聊天存档兼容成为重写的主工程。
- **你的答案 / 补充：** __B____

### Q18. LLM 和内容数据的联网边界是什么？

- A. 可以调用用户选择的在线 LLM；项目文件和音频默认留在本机
- B. 剧本生成也必须完全本地运行
- C. 将项目和素材托管到云端，方便多设备访问
- **推荐：A**。它保留模型选择空间，同时不在没有同步需求前引入云存储。
- **你的答案 / 补充：** __A____

## 第 4 轮：发布、上游与历史材料

这些决定会影响发布责任和后续维护方式。

### Q19. A2D 的软件许可证/发布方式希望是什么？

- A. 暂时沿用当前 AGPL-3.0，再核实代码和素材来源
- B. 未来希望更换许可证，先做来源/义务审查再决定
- C. 先只作为个人本地工具，不规划公开发行
- **推荐：A**。当前项目已带 AGPL-3.0；在查清上游代码、第三方素材和分发方式之前，不要贸然改许可证或发布新包。
- **你的答案 / 补充：** __A____

### Q20. 随软件提供的角色、图片和音频资源应该如何处理？

- A. 不预装角色资源，由用户导入自己的素材
- B. 只提供自行创作或授权清楚的示例资源
- C. 延续当前 LingChat 默认资源并在说明中注明来源
- **推荐：B**。示例能降低上手门槛，但每项资源都要有明确来源和使用许可。
- **你的答案 / 补充：** __B____

### Q21. 后续如何跟进 LingChat 上游？

- A. 定期把官方 develop/main 合并进来
- B. 只有 A2D 确实需要时才挑选/重做相关能力
- C. 停止同步，把当前代码完全独立维护
- **推荐：B**。保持对上游的学习和复用机会，同时避免继续被上游产品方向和版本变化牵着走。
- **你的答案 / 补充：** __B____

### Q22. 现有 `fic_*` 自动生成管线应该怎样处置？

- A. 纳入 A2D 核心自动 CP 功能，继续补全
- B. 暂时作为实验，按 A2D 项目格式和用户流程验收后再决定
- C. 归档，不再投入
- **推荐：B**。它可能支持 Auto CP，但模块存在不等于已经解决编辑、双人 TTS、播放和项目导出。
- **你的答案 / 补充：** __B____ 我已经差不多忘记这个是啥了

### Q23. 旧文档和历史日志应该如何收敛？

- A. 全部保留原样，只增加索引
- B. 先建立活跃文档索引，确认历史内容可查后再分批归档
- C. 现在删除过期文档和日志
- **推荐：B**。先减少误读和查找成本，同时保留问题根因与项目来历；暂不批量删除。

## 第 5 轮：定义成功标准和投入节奏

### Q24. 哪个结果可以算作 A2D 第一个真正完成的版本？

- A. 手写/编辑剧本、双路 GSV 合成、播放、保存并重新打开/导出全部跑通
- B. 输入主题后一键生成并播放完整 CP 故事
- C. 桌面和手机原生应用均可安装，带完整视觉效果
- **推荐：A**。它先证明 A2D 的创作产物确实能从脚本走到可复用内容；B 和 C 可建立在这条链路上。
- **你的答案 / 补充：** __A____

### Q25. 你更愿意按什么节奏推进？

- A. 每次只做一个短里程碑，验证后再开下一步
- B. 先做一轮较完整的重构，再统一验证
- C. 暂不设阶段，想到什么就逐项改善
- **推荐：A**。目前运行基线、产品格式和 Rust 方向都还需验证，小里程碑更容易及时纠偏。
- **你的答案 / 补充：** __A____
