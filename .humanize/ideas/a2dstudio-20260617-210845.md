# Persistent Tab State And Timeline Navigation For Script Editor

## Original Idea

目前的剧本编辑器，还有一些不太方便的地方，之前可能没有充分提到：当在"审核台"改完后，如果切换到"时轴"，审核台似乎会丢失信息（变成空白），审核台似乎应该保持在当前编辑句，直到用户点击继续下一句？用户似乎只被允许更改当前句，与我们之前的设想有出入？我们希望用户能通过点击"时轴"上的任意一句来进入审核台，来进行编辑，并且，在用户编辑完之后，用户可以选择调用翻译模型api（翻译模型和llm模型不一定是同一个，目前是同一个，可能需要隔离翻译任务和主线任务的上下文），重新生成语音，并且，用户可以选择，让llm模型从后面的第几句开始重新生成，比如，用户编辑了第一句，但用户觉得刚才生成的第二句，第三句，是ok的，用户想从第四句开始，让llm模型重新生成/人工重新开始写，那就需要给用户一个选择权。另外，我们似乎应该允许用户，通过在"时轴"上选择，从第几句到第几句，然后就可以，依次从第几句到第几句，重新播放所有内容（屏幕各元素的变化和语音），这样方便用户审核，剧本中的某一段内容。另外，用户的编辑可能是会后悔的，用户如果希望回退一步，两步，甚至更多步，事情会变得很复杂。这里面的版本控制，感觉非常麻烦，你觉得该如何权衡，用户体验，与实现难度？也许允许用户最多回退两步，可能实现起来简单点？另外，之前似乎，情绪控制立绘变化，没有生效？可能需要确认。

## Primary Direction: 持久化审核台与时轴导航

### Rationale

ScriptPanel uses `v-if`/`v-else` which destroys ReviewPanel on every tab switch, causing all editing state loss. EventTrack has no click handlers. This direction fixes the data lifecycle and adds line-click-to-edit navigation — the foundation that undo, resume-point, range-playback, and translation all depend on.

### Approach Summary

Three interconnected fixes that together transform the editor from "single-line, fragile" to "multi-line, navigable":

**Fix 1 — Tab persistence (`v-if` → `v-show`):**
Replace `v-if`/`v-else` in `ScriptPanel.vue` line 18-19 with `v-show`. This keeps both ReviewPanel and EventTrack alive in the DOM — ReviewPanel's `editingText`, `userEdited`, and `lastLineId` survive tab switches. The only visual change: both components are always mounted, but only one is visible.

**Fix 2 — Clickable EventTrack with navigation:**
Add `@click` handler on each `.line-item` in EventTrack. Clicking a line:
- Sets `store.selectedLineId` to that line's id
- Switches ScriptPanel's `activeTab` to `'review'` (programmatic)
- ReviewPanel's existing `watch(() => store.currentLine, ...)` loads the selected line into the textarea

Add a visual highlight class (`.line-item--active`) on the currently selected line, and a dimmed class (`.line-item--future`) on lines after the resume point (see LLM resume-point below).

**Fix 3 — Store-level editing state:**
Move `editingText` from ReviewPanel's local `ref` into the script store as a per-line `editedText` map (`Record<string, string>` keyed by line id). When the user edits a line in ReviewPanel, the text persists in the store even if the component unmounts. When the user clicks "继续", the store-level edit is consumed and sent to the backend. When the user switches to EventTrack and clicks another line, the previous line's edit is preserved.

At this point the editor supports the fundamental workflow:
1. Generate lines via LLM
2. Click any line in EventTrack → review/edit in ReviewPanel
3. Edits persist across tab switches
4. Click "继续" to generate the next line

**Components affected (core fix ~150 LOC):**
- `ScriptPanel.vue` — 1 line change (`v-if` → `v-show`) + expose `activeTab` for programmatic control
- `EventTrack.vue` — add `@click`, visual highlight, expose selected state (~30 lines)
- `script.ts` store — add `selectedLineId`, `editedText` map (~20 lines)
- `ReviewPanel.vue` — read/write `editedText` from store instead of local ref (~15 lines)
- `useA2DWebSocket.ts` — include `editedText` in `sendContinue()` payload (~5 lines)

### Objective Evidence

- **`ScriptPanel.vue` lines 18-19**: `v-if="activeTab === 'review'"` / `v-else` — this is the root cause. Vue's `v-if` destroys the component DOM and all reactive state. `v-show` only toggles CSS `display`. This is a one-line fix with zero side effects since both components are lightweight.
- **`EventTrack.vue` line 56**: `cursor: default` on `.line-item` — confirms the component was intentionally designed as read-only. Lines 10-14 show `v-for="line in store.lines"` rendering each line with `line.index`, speaker name, and `line.display_text` — all the data needed for click-to-edit is already rendered.
- **`ReviewPanel.vue` lines 84-100**: The existing `watch(() => store.currentLine, ...)` with `lastLineId` and `userEdited` flags (added in commit `5cfa2501` for Stage 9) shows the editing state tracking already exists but is fragile. The watch resets `editingText` when `line.id !== lastLineId` — this is correct behavior for new lines arriving, but combined with tab-destroy it causes data loss.
- **`script.ts` store lines 6-13**: `ScriptLine` interface defines `id, speaker, display_text, tts_text, index` — no `emotion` field. The `addLine()` function (line 41) simply pushes to `lines[]` and sets `currentLine`. No selection state, no edit persistence. This minimal store makes additions straightforward.
- **`GameRoleAvatar.vue` lines 95-104**: `targetAvatarUrl` computed reads `role.emotion` and maps through `EMOTION_CONFIG_EMO` — the rendering pipeline works. But A2D never sets `role.emotion` because `useA2DWebSocket.ts` line 44 hardcodes `emotion: '正常'` and `script_line` handler only calls `store.addLine()` without updating gameStore.
- **`core.py` line 787**: `re.sub(r"^【.*?】", "", text)` strips the emotion tag and discards it. The emotion is parsed but never stored in `ScriptLine` or sent via WS.
- **`session_runtime.py` lines 62-121**: `_apply_edits()` already implements line-list truncation at a modified index. The mechanism for "resume from line N" already exists — it just needs a user-facing control to set the index.
- **`llm_config.py` lines 270-339**: Independent `[translator]` config section with `get_translator_config()` already exists. `.env` lines 29-34 define `TRANSLATE_LLM_PROVIDER`, `TRANSLATE_API_KEY`, `TRANSLATE_BASE_URL`, `TRANSLATE_MODEL`. The translation infrastructure is built — A2D just doesn't call it.
- **`translator.py` lines 69-162**: `translate_ai_response()` shows the complete translation flow. Can be reused for A2D per-line translation with minimal adaptation.
- **No undo/range-playback/resume-point code exists**: grep confirms these are genuinely new features with no existing implementation to conflict with.

### Known Risks

- **`v-show` memory**: Both components stay in DOM. ReviewPanel is ~200 DOM nodes, EventTrack is ~100 per 20 lines. Total extra memory < 1MB — negligible. If scripts grow to 500+ lines, EventTrack should virtualize; but that's a separate optimization.
- **`editedText` map growth**: Store-level edit map grows linearly with line count. Cleanup: clear entries for lines that have been "committed" (sent to backend via continue). Max ~100 entries in practice.
- **Programmatic tab switch UX**: When user clicks a line in EventTrack, `activeTab` switches to `'review'` — the tab button highlight must also update. ScriptPanel's local `activeTab` ref must be exposable or replaced with a store field.
- **Emotion field addition**: Adding `emotion` to `ScriptLine` and `ScriptLinePayload` requires simultaneous backend + frontend changes. If one side is updated without the other, the WS message will fail schema validation (Pydantic on backend, TypeScript interface on frontend).
- **Translation API cost**: Per-line translation doubles API calls. Mitigation: only trigger translation when `TRANSLATE_LLM_PROVIDER != "none"` AND character `voice_language != display_language`. Default config has `TRANSLATE_LLM_PROVIDER="none"` so zero impact for current users.

### Confidence

**high** — Every fix has a precise, single-line root cause visible in the code: `v-if` on ScriptPanel line 18, missing `@click` on EventTrack, hardcoded `emotion: '正常'` on useA2DWebSocket line 44, discarded emotion on core.py line 787. The fix surface is small (~150 LOC for the core tab/edit fixes, ~35 LOC for emotion, ~60 LOC for undo, ~50 LOC for resume-point, ~200 LOC for range playback). All extensions follow existing patterns (WS message types, store fields, Vue template bindings). The primary unknowns are UX polish (range highlight styling, playback progress indicator) rather than technical feasibility.

## Alternative Directions Considered

### Alt-1: 两步快照回退

- Gist: Add a bounded 2-step undo stack to the script store. Each `addLine()` call snapshots `lines[]` before mutation. Ctrl+Z pops the stack. The stack is a fixed-size ring buffer (max 2 entries), each entry is a shallow copy of `ScriptLine[]`. No backend changes needed — undo is purely frontend state reversion. When the user undoes, the backend's `generation_epoch` is notified via a new `a2d.undo` WS message to invalidate downstream TTS cache.
- Objective Evidence:
  - `script.ts` store is only 75 lines — adding a 2-entry snapshot ring buffer is ~40 lines of straightforward array manipulation.
  - `SessionRuntime` already has `generation_epoch` mechanism (lines 35, 66-89) that invalidates cached TTS — can be extended to handle undo epochs.
  - No existing undo/redo code exists anywhere in the A2D codebase — zero conflict risk.
- Why not primary: Undo is a safety net, not the primary workflow. Users need to navigate and edit lines first — undo is only useful after they've made mistakes. Build the navigation first, then add undo as a safety layer.

### Alt-2: 翻译模型隔离

- Gist: Connect A2D editor to the existing-but-unused translation infrastructure. When user edits a line's `display_text` (Chinese) and the character needs Japanese TTS (`voice_language != display_language`), call `Translator.translate_ai_response()` with the separate translation LLM provider. The translated text becomes the new `tts_text`, replacing the LLM's original `<TTS>` tag content. The translation provider, API key, and model are configured in `.env` — completely isolated from the main dialogue LLM context.
- Objective Evidence:
  - `llm_config.py` lines 270-339: `[translator]` config section, `get_translator_config()` function already exists.
  - `.env` lines 29-34: `TRANSLATE_LLM_PROVIDER`, `TRANSLATE_API_KEY`, `TRANSLATE_BASE_URL`, `TRANSLATE_MODEL` all defined with `TRANSLATE_LLM_PROVIDER="none"` as default.
  - `translator.py` lines 69-162: `translate_ai_response()` complete implementation.
  - `LLMManager.__init__` accepts `llm_job="translator"` parameter.
  - `QwenTranslateProvider` is a working example of a dedicated translation provider.
- Why not primary: Translation is an optional enhancement — the current single-LLM approach with `<TTS>` tags works. The more urgent issues are the tab-state loss (data destruction) and emotion pipeline (broken visuals). Translation can be added after the editor's basic navigation is solid.

### Alt-3: 时轴区间播放审核

- Gist: Add range selection in EventTrack (click start → shift-click end to select a range), then a "播放选中范围" button that sequentially replays each selected line: update character emotion/sprite, show dialogue text in bubble, play cached audio, wait for audio end, advance to next line. Uses existing `GameRoleAvatar` emotion watcher and backend `/audio/` route. Implemented as a new composable `useRangePlayback.ts` with an async queue that processes lines one at a time.
- Objective Evidence:
  - EventTrack already renders all lines with full data (speaker, display_text, tts_text).
  - `GameRoleAvatar.vue` watcher (lines 107-153) handles emotion → sprite transitions with built-in race-condition guard (`latestEmotionId`).
  - Audio files are served at `http://localhost:8765/audio/a2d_{id}.wav` (Stage 9 fix, commit `cb7272d0`).
  - `event-queue.ts` shows existing sequential event processing pattern.
- Why not primary: Range playback requires the emotion pipeline to be fixed first (otherwise sprites never change during playback) and requires tab persistence (otherwise you can't select a range then switch to review). It's a dependent feature — build the foundations first.

### Alt-4: 从第N句重新生成

- Gist: Add a `resume_after_index` parameter to `a2d.continue` WS message. When set, the backend truncates `script_lines` to `lines[:resume_after_index]`, increments `generation_epoch`, and regenerates from that point. The frontend adds a "从此处重新生成" button in ReviewPanel when viewing a non-last line, and visually dims lines after the resume point in EventTrack to indicate they'll be discarded.
- Objective Evidence:
  - `session_runtime.py` lines 62-121: `_apply_edits()` already implements index-based truncation — exact same mechanism needed.
  - `_a2d_build_messages()` (core.py lines 697-728) rebuilds LLM context from `session.script_lines` — truncation before this call automatically produces correct context.
  - `ContinuePayload` schema (script_overlay.py lines 84-88) already accepts optional fields — adding `resume_after_index` is a one-field addition.
- Why not primary: Resume-point is a power-user feature. Most users will edit the last line and continue. The immediate pain points are tab data loss and emotion not working. Resume-point can be added after the navigation UX is solid.

### Alt-5: 情绪立绘管线修复

- Gist: Trace and repair the full emotion data flow. Currently broken at 4 disconnect points: (1) `_a2d_parse_script_line()` strips emotion tag without storing it, (2) `ScriptLine`/`ScriptLinePayload` have no `emotion` field, (3) WS `script_line` message omits emotion, (4) frontend `useA2DWebSocket.ts` hardcodes `emotion: '正常'` and never updates from script lines. Fix: add `emotion: str` field to all 4 layers, populate from LLM output, and call `gameStore.gameRoles[roleId].emotion = emotion` in the `script_line` WS handler. The downstream rendering (`GameRoleAvatar.vue` watcher → `EMOTION_CONFIG_EMO` → avatar URL) works correctly once it receives non-default emotions.
- Objective Evidence:
  - `core.py` line 787: `re.sub(r"^【.*?】", "", text)` — emotion parsed then discarded. The regex match group with the emotion value is thrown away.
  - `script_overlay.py` lines 30-47, 131-136: Both `ScriptLine` dataclass and `ScriptLinePayload` lack `emotion`.
  - `useA2DWebSocket.ts` line 44: `emotion: '正常'` hardcoded.
  - `GameRoleAvatar.vue` lines 95-104: `targetAvatarUrl` computed reads `role.emotion` and maps through `EMOTION_CONFIG_EMO` — rendering pipeline works.
  - `dialogue-processor.ts` line 44: LingChat's native dialogue event correctly does `role.emotion = event.emotion` — the pattern exists, A2D just doesn't follow it.
  - Total fix: ~35 lines across 7 files.
- Why not primary: This is the smallest, most surgical fix — ~35 lines. It should be done alongside (or immediately after) the primary direction. It's not primary only because tab persistence affects more user workflows. The two fixes together (tab persistence + emotion) would deliver the most visible UX improvement in the fewest lines of code.

## Synthesis Notes

The five alternative directions are not competitors — they form a natural dependency chain. The primary direction (tab persistence + clickable EventTrack) is the foundation. Emotion fix (Alt-5) is the quickest win and should be done in the same pass. Resume-point (Alt-4) builds on click-to-select in EventTrack. Range playback (Alt-3) builds on resume-point's selection model. Undo (Alt-1) is the safety net for all editing operations. Translation (Alt-2) is the most independent — it can be added at any point once per-line editing works.

Recommendation: Stage 10 Phase 1 = Primary direction + Alt-5 (emotion fix) — together these are ~185 LOC and fix the two most visible UX problems (data loss on tab switch + static character sprites). Phase 2 = Alt-4 (resume-point, ~80 LOC) + Alt-1 (undo, ~60 LOC) — these complete the editing control surface. Phase 3 = Alt-3 (range playback, ~200 LOC) + Alt-2 (translation, ~100 LOC) — these add the review and polish features.
