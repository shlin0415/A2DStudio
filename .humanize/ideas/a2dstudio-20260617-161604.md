## Primary Direction: 手动控制优先的剧本编辑器

### Rationale

All four features (auto-CP, auto-media, script editor, ASMR) depend on the core script editor being complete; the 7 todo items map 1:1 to extending already-built components (ReviewPanel, EventTrack, ScriptPanel), making this the lowest-risk, highest-leverage starting point.

### Approach Summary

Complete the script editor's manual control surface first — before adding auto modes or new feature wrappers. Build on the existing A2D components already working in the Python/Vue codebase (not the Rust prototype):

**Layer 1 — LLM Transparency (todo items 1-2):**
- Add a "Preview LLM Context" panel that shows the full system prompt + message history + current instruction before the user starts generation. Reuse the existing `prompt_lines` list in `ling_chat/core/ai_service/core.py` to extract the complete LLM input.
- Add a "Handwrite Mode" toggle in ReviewPanel that disables LLM calls entirely. When active, the user types display_text + TTS text directly, and submits manually. The existing `_generate_and_synthesize()` pipeline is bypassed via a `handwrite_mode` flag in the session.

**Layer 2 — Manual Controls (todo items 3-4):**
- Add a speaker selector dropdown in ReviewPanel that lets the user override which character speaks next. On the backend, wrap the existing LLM speaker selection in a check: if `manual_speaker` is set, skip LLM speaker decision and use the user's choice.
- Add a "Hint Injection" textarea that appends a temporary instruction to the next LLM call. Backend: append `[剧本家提示: {hint}]` to the message before sending to LLM.

**Layer 3 — Content Overlay (todo item 5):**
- Add an overlay editor for images and text on top of the character stage. Use relative-positioned divs in `StageView.vue` with drag-to-move and corner handles for resize. Store overlay state in the Pinia script store and serialize to the export.

**Layer 4 — Export & Playback (todo items 6-7):**
- Add an "Export Script" button that collects all script lines (display_text, TTS text, audio files, overlays, speaker, emotion) into a folder. The folder layout: `{script_name}/lines.jsonl`, `audio/` (symlinks or copies of WAV files), `overlays/` (images), `script.md` (human-readable dialogue). Reuse the existing backend `/audio/` route for audio file access.
- Add a "Galgame Playback" mode that hides the editor panels and shows only the character stage + speech bubbles, advancing on click/tap. This is a CSS class toggle + auto-advance disable in the existing `StageView.vue`.

**Components affected:**
- Backend: `ling_chat/core/ai_service/core.py` (prompt preview endpoint, handwrite mode flag, hint injection)
- Backend: `ling_chat/core/a2d_message_handler.py` (new WS message types: `a2d.preview_prompt`, `a2d.set_mode`, `a2d.inject_hint`, `a2d.export`)
- Frontend: `ReviewPanel.vue` (speaker selector, handwrite toggle, hint textarea)
- Frontend: `StageView.vue` (overlay editor, galgame playback mode)
- Frontend: `useA2DWebSocket.ts` (new message type handlers)
- Frontend: `scriptStore.ts` (overlay state, mode state, export trigger)
- New: `OverlayEditor.vue` (image/text placement + resize)

### Objective Evidence

- **`frontend_vue/src/components/game/ReviewPanel.vue`** (existing, ~200 lines): Already has editable textarea, "regenerate TTS" button, dirty-flag tracking (`userEdited`, `lastLineId`). The speaker selector and handwrite toggle are direct additions to this component's template and script.
- **`frontend_vue/src/components/game/EventTrack.vue`** (existing): Line history list with click-to-select. Can serve as the navigation UI for galgame playback (click line → jump to that point).
- **`frontend_vue/src/components/game/ScriptPanel.vue`** (existing): Tab container already switching between ReviewPanel and EventTrack. A third tab for "Export" or "Overlays" follows the same pattern.
- **`ling_chat/core/ai_service/core.py`** (existing, prompt system): The `prompt_lines` list already builds the full LLM prompt programmatically. Exposing this as a preview endpoint requires only serializing `prompt_lines` to a string and returning via WS.
- **`ling_chat/core/a2d_message_handler.py`** (existing, WS dispatcher): Already handles `a2d.start`, `a2d.continue`, `a2d.retry`, `a2d.regenerate_tts`. Adding new message types follows the same `elif msg_type == ...` pattern.
- **`frontend_vue/src/composables/useA2DWebSocket.ts`** (existing): Already handles audio playback, store updates, error classification. New message types add ~10 lines each.
- **`frontend_vue/src/views/StageView.vue`** (existing): Already hosts GameRolesStage + ScriptPanel. The galgame playback mode is a `v-if` toggle hiding ScriptPanel and showing only the stage + dialog bubble.
- **`frontend_vue/src/stores/scriptStore.ts`** (existing): Already holds `currentLine`, `lines[]`, `isThinking`, `isSynthesizing`. Adding `handwriteMode`, `manualSpeaker`, `pendingHint`, `overlays[]` extends the same interface.
- **`frontend_vue/src/components/game/GameRolesStage.vue`** (LingChat, reused): Already renders character sprites with CSS transitions. Overlay divs with relative positioning can be layered on top without modifying GameRolesStage.
- **Export precedent** in reference projects: N.E.K.O's `plugin/message_plane/main.py` has a chat log export function. SillyTavern's `export` command in `public/scripts/group-chats.js` exports chat history as JSON. The export folder format follows these established patterns.
- **No existing export, overlay editor, or handwrite mode**: grep confirms these are genuinely new features — no dead code to remove, no conflicting implementations.

### Known Risks

- **Handwrite mode + TTS regen interaction**: When the user types TTS text manually, the `gsv_voice_text` reference check (from Stage 9) must still validate. If handwrite mode bypasses the LLM's `<TTS>` tag parsing, we need a fallback path that accepts raw text for TTS.
- **Overlay editor on GameRolesStage**: The stage uses CSS transforms for character positioning; overlays positioned via absolute coordinates may drift when the viewport resizes. Mitigation: store overlay positions as percentages of stage dimensions.
- **Export with external audio files**: Audio files live in `ling_chat/data/temp_voice/` and may include cached files from previous sessions. The export must filter to only the audio files referenced by the current script's lines.
- **Galgame mode state conflict**: The existing `isThinking`/`isSynthesizing`/`paused` state machine in `scriptStore` was designed for the editor flow. Galgame playback adds a `playing` state that auto-advances through lines. These states need clear priority rules.
- **Prompt preview performance**: The full LLM context can be thousands of characters; sending it via WS to the frontend for every "preview" click may cause UI lag. Mitigation: send once on mode entry, cache in frontend, update only when user injects hints or changes speaker.

### Confidence

**high** — Every todo item maps to a specific existing component with a clear extension path. The codebase already has the editor shell (ReviewPanel + ScriptPanel + EventTrack), the WS protocol pattern (a2d_message_handler.py), the prompt construction (core.py), and the character stage (GameRolesStage). The 7 features are additive UI work with no architectural refactoring required. The primary unknowns are UX polish (overlay drag handles, galgame playback smoothness) rather than feasibility.

## Alternative Directions Considered

### Alt-1: 统一模式切换

- Gist: Treat all four features as mode presets that change LLM prompt + TTS params + UI overlays without new routes or components. A `modePreset` reactive ref in the Pinia store switches between "script-editor", "auto-cp", "media-tool", and "asmr" modes, each triggering a batched settings override (prompt suffix, TTS speed/volume, visible UI panels).
- Objective Evidence:
  - Rust LingChat-tauri-refactor has `enterStoryMode()`/`exitStoryMode()` as a binary mode switch pattern; extending to 4-way is straightforward.
  - Settings store already supports hierarchical dot-path updates and import/export — preset persistence is trivial.
  - Single-page `/chat` route already handles all interaction modes without new Vue Router entries.
- Why not primary: This direction packages features as presets before the editor's manual controls are complete — putting the cart before the horse. The editor must work manually before it can be automated.

### Alt-2: 导出与播放管线优先

- Gist: Build the export/packaging format and playback pipeline as the output surface shared by all four features. Define a self-contained "playable bundle" format (ZIP or folder with event sequence JSON, media assets, pre-generated TTS audio, metadata). Build a headless playback engine that reads from the bundle and emits events to the existing frontend event queue.
- Objective Evidence:
  - Rust codebase has `zip` crate already in Cargo.toml for `data_update/sync.rs` downloads — packaging pattern exists.
  - Frontend `EventQueue`/`EventProcessorManager` already processes sequential events with duration-based auto-advance — playback would push events into the same queue.
  - `VoiceMaker` batch TTS and `AudioAcrossFade` cross-fade components exist for audio pre-generation and seamless transitions.
- Why not primary: Export is the last step in the workflow, not the first. Without manual editing controls, there's nothing worth exporting. Build the editor first, then the export format naturally follows.

### Alt-3: 场景模板驱动

- Gist: Each feature is a `SceneTemplate` struct with preset LLM prompts, TTS settings, UI layout constraints, content constraints (max LLM calls, max turns, auto-stop), and fallback/rotation behavior for ASMR. A template selector UI replaces the current single-purpose editor UI. Similar to SillyTavern's character cards and N.E.K.O's session configs.
- Objective Evidence:
  - Rust codebase has `SceneStore` (JSON file persistence, `load_all()`/`save_all()`/`find_by_id()`) — directly applicable pattern.
  - `CharacterSettings` uses `#[serde(flatten)] extra: HashMap` for schema-less extension — same pattern for template fields.
  - `GameStatus` already has `current_scene_id: Option<String>` field ready for template tracking.
- Why not primary: ASMR-specific features (sleep timer, LLM budget, auto-stop, audio carousel) have zero existing precedent in our Python codebase — ~30% of this design is unvalidated. The template abstraction also adds a new concept to learn before the base editor is solid.

### Alt-4: 内容类型路由

- Gist: Build a `ContentType` enum (SocialMedia, CpStory, Script, Asmr) that dispatches to different LLM prompts, TTS profiles, and UI layouts. The mode is inferred from what content the user is creating. The dispatch system mirrors LingChat's existing event registry pattern (`LazyLock<RwLock<HashMap<&str, EventFactory>>>`).
- Objective Evidence:
  - Rust codebase has three separate type-based dispatch subsystems: script event registry, LLM provider routing (`LlmRoleAssignment`), and TTS adapter selection (`TtsProvider::select(tts_type)`).
  - Frontend `GameModeOptions.vue` already lists "自由对话模式", "剧情模式" — adding ASMR and media modes follows existing UI convention.
  - Python LingChat's `EventHandlerLoader` uses `importlib` to auto-discover event handlers — same pattern for content-type handlers.
- Why not primary: The content-type abstraction is elegant but premature. The distinctions between "auto-cp story" and "ASMR story" are primarily in prompt tone and TTS params — both can be achieved with simpler prompt suffix injection rather than a full routing system. Also requires new backend infrastructure for cost tracking (no token counting exists).

### Alt-5: 后端优先的批量内容生成

- Gist: Build a headless batch content generation service first — a `BatchContentGen` module with a job queue, background executor loop (patterned after `ProactiveSystem`'s 30s tick), and progress streaming via existing Tauri/WS event channels. Thin UI layers (editor, media-tool, ASMR mode) become optional frontends reading from the same event stream.
- Objective Evidence:
  - Full LLM→TTS→audio pipeline exists but is interactive-only — triggered by `send_chat_message` or `ProactiveSystem::run_cycle`.
  - Background loop pattern exists in multiple places: `ProactiveSystem` (30s interval), `AutoSaveManager` (5min interval), both using `tokio::spawn` + `Arc<Mutex<>>`.
  - `MessageGenerator::run_pipeline()` already spawns a concurrent consumer pool — directly reusable for batch.
- Why not primary: Batch generation requires cost tracking and token budget enforcement, but the codebase has zero token counting infrastructure. The `generation_lock` serializes all LLM calls — batch jobs would block interactive use. Also, the user's primary concern is the manual editing experience, not headless generation.

## Synthesis Notes

If the user prioritizes shipping a working "auto-CP story generator" quickly, folding Alt-1 (Mode-as-Preset) into the primary direction would be the fastest path: complete 3-4 manual controls first, then add a mode dropdown that swaps prompt suffixes and TTS presets. The ASMR mode specifically benefits from Alt-3 (Scene Template) for its unique constraints — sleep timer, turn limits, audio carousel — but those can be added as optional settings within the editor rather than a separate architectural layer. Alt-2 (Export Pipeline) is the natural end-state of the primary direction: once manual editing works, the export format emerges from the data model already in `scriptStore.lines[]`. Alt-5 (Backend-First) is the right approach if the user later wants "set it and forget it" overnight CP story generation, but that requires token tracking infrastructure that doesn't exist yet. The recommendation is to stay with the primary direction (manual controls) for Stage 10, cherry-pick the mode toggle from Alt-1 as a Stage 10b stretch goal, and defer the export/pipeline work to Stage 11.
